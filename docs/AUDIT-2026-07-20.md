## PART 1 — Runaway CPU/RAM: ROOT CAUSE (confirmed, not inferred)

**It was not ClickHouse.** ClickHouse was `Exited (0)` the whole time. Two SigNoz
containers were in a perpetual crash-restart loop.

```
kerjacus-signoz-otel-collector-1   Restarting (1)   405 restarts   policy=on-failure max=0
kerjacus-signoz-query-service-1    Restarting (1)   405 restarts   policy=on-failure max=0
```

Restart interval ~62s, running continuously for 7 weeks (405 × ~62s). `restart: on-failure`
with `MaximumRetryCount=0` means **Docker retries forever**. Every 62s two Go binaries
cold-start, fail, and die — plus dockerd churn. On WSL2 that is permanent background load.

**Action taken:** both containers stopped. Loop is dead. (`docker start <name>` reverses it.)

### Fatal 1 — otel-collector: config file never mounted

```
failed to get config: cannot retrieve the configuration: unable to read the file
file:/etc/otel-collector-config.yaml: open /etc/otel-collector-config.yaml: no such file or directory
```

`docker-compose.yml:285-299` passes `--config=/etc/otel-collector-config.yaml` but mounts only
`signoz_collector_data:/var/lib/signoz`. The config file `apps/gateway/otel-collector-config.yaml`
exists on disk and **is** mounted in `docker-compose.prod.yml:354` — the dev file just omits it.

### Fatal 2 — query-service: sqlite dir never mounted

```
Failed to create signoz struct: unable to open database file: no such file or directory
```

`SIGNOZ_LOCAL_DB_PATH: /var/lib/signoz/signoz.db` but `docker-compose.yml:301-310` declares **zero
volumes**. Prod mounts `kerjacus_signoz_query:/var/lib/signoz`; dev does not.

## PART 2c — ClickHouse: two unpatched HIGH RCE CVEs

Separate from the crash-loop, the pinned ClickHouse version is a genuine security problem.
`24.1` was never an LTS; its last build was `24.1.8.22` on **2024-03-26** — over two years EOL.

| CVE | Severity | Fixed in | Status on 24.1.x |
|---|---|---|---|
| CVE-2024-6873 | **High** — RCE via native interface | 24.3.4-lts, 24.4.2, 24.5.1 | **Unpatched.** Fix skipped 24.1/24.2 entirely; branch was already dead |
| CVE-2025-1385 | **High** — RCE via library-bridge | 24.3.18.6, 24.8.14.27, 25.1.5.5 | **Unpatched.** Never backported |

Affects `clickhouse-server:24.1-alpine` (dev) and `24.1.2-alpine` (prod/Langfuse).
Supported LTS today: **26.3** (current) and **25.8**. `latest` currently resolves to 26.6 —
and being unpinned, silently moves on every redeploy.

**My earlier cgroup theory was wrong, and it's worth recording.** I suspected ClickHouse was
ignoring `mem_limit` and sizing itself from host RAM. It does not: `memory_worker_use_cgroup`
and `memory_worker_dynamic_hard_limit` both default to `true`, and the hard limit is
recomputed against the cgroup limit. `max_threads=0` (auto) has been cgroup-CPU-quota-aware
since 2022. The real gap is narrower: **thread-pool ceilings are hardcoded constants that
never auto-scale** — `max_thread_pool_size=10000`, `background_schedule_pool_size=512`,
`background_pool_size=16` (ClickHouse's own issue #93710, filed by staff 2026-01-08, still
open). Plus a confirmed idle-CPU bug: `AsynchronousInsertQueue` busy-polls at ~1590
wakeups/sec with zero load (issue #106160, still open).

Both are only relevant if we keep ClickHouse at all — see the decisions section.

OpenSearch, Redpanda, Kafka, MongoDB, Prometheus and Postman are all **absent** — grepped the

## PART 4 — License Audit

Scope: every image pulled or built by `docker-compose.yml` / `docker-compose.prod.yml`, checked
against each project's own LICENSE file or an official statement — no claim below is from memory.
Two housekeeping notes before the findings: PART 2d's `Langfuse` and `SigNoz` rows ("gated off;
needs a decision") describe an earlier state of both compose files — both have since been **removed
outright**, not gated, from dev and prod alike, replaced by `openobserve` (§4e covers the licence
angle on that swap). ClickHouse is gone with them; PART 2c's two unpatched CVEs no longer apply to
anything currently in either compose file. For the record, neither was ever a licensing problem:
ClickHouse core is [Apache-2.0](https://github.com/ClickHouse/ClickHouse/blob/master/LICENSE),
unchanged since 2016, and ClickHouse Cloud is a separately-priced hosted product running the same
OSS engine, no proprietary fork. SigNoz is MIT core with a separate proprietary "SigNoz Enterprise
License" gating `ee/`-directory features (SSO, audit log) behind a subscription — open-core like
Langfuse and Flagsmith, not SSPL. Both were removed for CVE exposure and resource footprint
(PART 1, PART 2c), never for licensing.

### 4a — Redis → Valkey: correct call, one stale comment, one bug already caught and fixed mid-audit

The swap from `redis:7-alpine` (7.x line, dual-licensed RSALv2/SSPLv1 — not OSI-approved) to
`valkey/valkey:9-alpine` (BSD-3-Clause, Linux Foundation-governed fork) is licensing-sound and
already live in both files. [Valkey LICENSE](https://github.com/valkey-io/valkey/blob/unstable/COPYING).

- **Dev comment was confusing, not wrong — reworded.** The claim that "the official `valkey/valkey`
  image does not ship a `redis-cli` symlink" is **incorrect**, verified directly:
  `ls -la /usr/local/bin/redis-cli` inside `valkey/valkey:9-alpine` returns
  `redis-cli -> valkey-cli`. The symlink is there, and `redis-cli SET/GET/DEL` were run
  successfully against the live container. The real problem was narrower: the comment offered
  "so the healthcheck works as-is" as its justification while the healthcheck had been switched
  to `valkey-cli` anyway, so it explained a decision that wasn't taken. Comment reworded.
- **Prod had a real bug; it's fixed now.** An earlier read of `docker-compose.prod.yml` during this
  same audit pass showed the `valkey` service renamed correctly, but its consumers not updated:
  `auth-service` had `depends_on: redis` and `REDIS_URL: redis://redis:6369` against a hostname that
  no longer existed, `project-service` had the same dangling `REDIS_URL`, and the top-level `volumes:`
  block declared an orphaned `kerjacus_redis_data` while never declaring the `kerjacus_valkey_data`
  actually mounted — two of those are hard `docker compose` validation failures, not runtime
  surprises. Re-reading the file just now: all of it is fixed — `auth-service` depends on `valkey`
  and points at `redis://valkey:6379` (`docker-compose.prod.yml:297,310-311`), `project-service` no
  longer references Redis/Valkey directly at all, and `volumes:` cleanly declares only
  `kerjacus_valkey_data` (`docker-compose.prod.yml:503`). Nothing left to fix — noted for the record
  since it was caught in-flight.

### 4b — KeyDB: not deployed, evaluated on request. Verdict: don't.

KeyDB itself is [BSD-3-Clause](https://github.com/Snapchat/KeyDB), Snap Inc.-owned since May 2022 —
the licence is not the problem. The problem is maintenance: Snap's own docs still describe it as
actively developed ([docs.keydb.dev](https://docs.keydb.dev/docs/about/)), but a GitHub issue from
October 2025 reports no meaningful commit activity since 2023
([Snapchat/KeyDB#923](https://github.com/Snapchat/KeyDB/issues/923)), and that's consistent with the
repo's own visible activity. Be blunt: KeyDB reads as de facto abandoned. Valkey (already chosen) has
Linux Foundation governance, a real release cadence, and is protocol-compatible with the same
`redis://` clients this stack already uses — there is no scenario where KeyDB is the better pick here.

### 4c — MinIO: AGPLv3, upstream repo archived, binary distribution model changed under it

Unchanged from the earlier status check, restated here for the permanent record and because it
directly parallels 4e below. `minio/minio` is
[AGPLv3](https://github.com/minio/minio/blob/master/LICENSE). The
[repo](https://github.com/minio/minio) moved to "no longer maintained" on 2026-02-12 and was archived
(read-only) on 2026-04-25 — three months ago as of this audit, not a future risk. Community-edition
pre-compiled binaries are no longer being published going forward; the project is source-only from
here. `docker-compose.yml:70` and `docker-compose.prod.yml:95` both still pull `minio/minio:latest`,
which will keep resolving to whatever the last-published community tag was, indefinitely.

AGPLv3's network-copyleft clause (§13) triggers on **modifying and then offering** the modified
program as a network service. BYTZ runs MinIO unmodified as internal object storage behind its own
proprietary services — end customers (project owners, talents) never interact with MinIO directly —
so this does not currently obligate source disclosure. That reasoning holds only as long as the image
stays unmodified and unforked.

### 4e — OpenObserve: the SigNoz/ClickHouse replacement is AGPLv3, not Apache-2.0

New since the original scope — `openobserve` didn't exist in this stack when this audit started; it
was added to replace SigNoz+ClickHouse (PART 2c/2d) in both compose files, and it deserves the same
scrutiny as everything it replaced. `docker-compose.yml:251-256` justifies the swap by citing the
exact two ClickHouse CVEs from PART 2c — good, that means the fix was informed by this audit. What
the comment doesn't mention: **OpenObserve itself is AGPLv3**, not Apache-2.0. It shipped Apache-2.0
originally and [switched to AGPLv3 in November 2023](https://openobserve.ai/blog/what-are-apache-gpl-and-agpl-licenses-and-why-openobserve-moved-from-apache-to-agpl/)
for the same reason most source-available pivots happen — open-core sustainability — and now sells a
[separate commercial Enterprise Edition](https://openobserve.ai/enterprise-license/) (SSO, RBAC) for
teams that can't take AGPL. [LICENSE](https://github.com/openobserve/openobserve/blob/main/LICENSE).

Net effect: this stack traded a concrete, unpatched RCE risk (good trade) for a second AGPLv3
component alongside MinIO (a licensing-posture fact, not a blocker). Same reasoning as 4c applies —
unmodified internal use, not exposed to end customers as its own service, doesn't trigger §13. No
swap recommended. Two things worth doing: keep it pinned to `v0.91.2` as it now is (don't drift to
`:latest`), and don't carry local patches to the OpenObserve source if the team ever needs a custom
feature — that's exactly the scenario that would trigger disclosure.

## PART 6 — Corrections found after the first pass

Follow-up research contradicted four things. I re-measured each rather than trusting either
side; two corrections were right, two were wrong.

### Corrections that were right — fixed

| Claim | Verified how | Action |
|---|---|---|
| `ZO_TELEMETRY_ENABLED` is not the real var | My container was logging `sending a track event OpenObserve - Starting server` — the var was silently ignored and it **was** phoning home. `ZO_TELEMETRY=false` gives 0 telemetry log lines | Fixed |
| OpenObserve is AGPL-3.0, not Apache 2.0 | Fetched the repo `LICENSE` — "GNU AFFERO GENERAL PUBLIC LICENSE Version 3" | CLAUDE.md corrected in 2 places |
| `latest` is one version stale | `v0.91.2` pulls and runs | Pinned v0.91.1 → v0.91.2 |

Also found while testing: **the disk cache is host-derived too**, not just memory. Defaults on
this box gave a **397 GB** disk cache. Added `ZO_DISK_CACHE_MAX_SIZE`.

### Corrections that were wrong — kept my version

| Claim | What I measured |
|---|---|
| "`ZO_MEMORY_CACHE_MAX_SIZE` does not exist in the env-var reference" | A/B test, same image, same everything else: **without it → `MEM max size 6.85 GB`; with it → `MEM max size 256.00 MB`**. The suggested replacement `ZO_MEM_TABLE_MAX_SIZE` left it at 6.85 GB. The var is undocumented, not absent — and it is the correct knob |
| "The Valkey image ships `valkey-cli`, not `redis-cli`, so your healthcheck will fail" | `ls -la /usr/local/bin/redis-cli` → `redis-cli -> valkey-cli`. The symlink exists; the old healthcheck would have kept working. I had already switched to `valkey-cli` anyway, for explicitness |

### MinIO — upstream looks dead

`minio/minio:latest` resolves to **`RELEASE.2025-09-07T16-13-09Z`** — roughly ten months stale,
consistent with reports that MinIO stopped publishing open-source images in late 2025, moved to
maintenance mode, and archived the repository in April 2026. I could not reach the GitHub API
from this environment to confirm the archival directly, so treat that specific date as
**reported, not verified here**. What *is* verified: the tag is frozen and the licence is AGPLv3.

Impact is limited — MinIO is only a local stand-in for Cloudflare R2, which is the real
production target. But `:latest` will never move again, so there is no future patch path.
Worth planning a swap (SeaweedFS, Garage, or just pointing dev at R2 directly).
