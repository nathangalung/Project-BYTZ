# Audit 2026-08-17: performance, correctness and coupling across apps/

Eight readers over `apps/`, each capped at four findings, every finding then handed to a
separate agent told to refute it by default. Thirty of forty went to verification, twenty-four
survived, six were refuted. Three of the survivors I then re-derived myself from the source
before acting on them; the rest carry the agents' verification only, and the difference is
marked on every entry below.

## What was measured

Nothing. Every finding here is reasoning over source. There is no load testing tool in this
repo, no `k6` script, no `k6/http` import, no entry in any manifest, so the numbers in
CLAUDE.md's Performance Requirements section (200ms API P95, 500ms with a database query, 1000
requests per minute, 500 concurrent users) are targets nobody has generated load against.
Nothing in CI would notice one being missed by a factor of ten.

What the verification pass established is mechanism, not magnitude. All thirty verdicts came
back with a corrected magnitude, including every finding whose mechanism survived intact: one
claim of eighty requests was about thirty-one, one of 250,000 rows scanned was about 50,000, one
of a thousand rows a year was about 250. Not one number arrived intact. Read every quantity
below as an estimate from code shape and schema, and re-derive it before planning against it.

Two other measurements that did not become findings, because they turned out to be handled.
Web ships 2.1MB of JavaScript and admin 1.2MB, with recharts the largest single chunk at 348KB,
but `heavy-chunk-loading.test.ts` already pins recharts behind a `Suspense` boundary that only
resolves when there are rows to plot, the SVAR Gantt behind its tab, and a per-second timer
inside a leaf component so it stopped rebuilding a 600-line page every second. The splitting is
correct and guarded.

## Fixed in this pass

### A checkout named its kind twice and nothing compared the two

Verified independently, then fixed in `5781368`.

`checkout.tsx` mints the Midtrans order id with a kind prefix and sends `checkoutType` beside it
as a separate field. payment-service priced from `checkoutType` alone, through
`GetCheckoutAmount`. project-service decided what the payment unlocked from the other field,
through `parseOrderRef` and the switch in `PaymentSettlementService.settle`. Nothing compared
them.

One authenticated POST with `checkoutType: "brd"` and an order id starting `PRD-` passed the
ownership check, charged 99,000, and stamped `prd_documents.paid_at` on settlement: the 199,000
entitlement, its watermark-free download and revisions to v9, for the cheaper document. It works
in either direction, needs no race, and the idempotency key never caught it because each
checkout mints a fresh order id, leaving the amount-mismatch conflict unreachable.

`CreateSnapToken` now requires the prefix to match the checkout type. That also closes a quieter
hole: an unrecognised prefix settles as `unknown order prefix`, so the money moved and nothing
was granted. Twelve tests were using `ORD-` ids with a valid checkout type and passing straight
through that path.

This is defence in depth, not the whole fix. See the open item below.

### Cancellation refunded the escrow before checking the cancellation was allowed

Verified independently, then fixed in `8a8f35a`.

`POST /projects/:id/transition` refunded first and validated second. The refund commits in
payment-service in its own cross-service transaction, and the throw from `transitionStatus`
cannot roll it back.

`VALID_TRANSITIONS` has `review: ['completed', 'disputed']`, so cancelling from review is
deliberately refused, while residual escrow at review is ordinary: `in_progress` to `review` is
a valid manual target and nothing requires milestones to have been released first. The owner
moved to review, posted `cancelled`, got the refusal, and the remaining milestones became
unpayable against an emptied escrow account. Same shape from `completed`, `brd_purchased`,
`prd_purchased` and `cancelled`, which all permit nothing.

The money-before-status ordering is kept for cancellations that are allowed, because it exists
to protect against refund failure. Validate, then refund, then transition.

### Every invoice PDF for a project could land on the same object

Verified independently, then fixed in the commit carrying this document.

`invoiceNumberForMilestone` derives its sequence from `COUNT(DISTINCT milestone_id)` and then
inserts, so two settlements of the same project can both read the same count before either
writes and produce the same `INV-XXXX-0001`. The unique constraint that would have rejected that
was dropped in migration 0019, correctly: three audience copies share one number per milestone,
so the replacement unique is `(milestone_id, audience)`.

The object key, however, was `invoices/{projectId}/{invoiceNumber}-{audience}.pdf`. Two
milestones sharing a number wrote to one key, the second upload replaced the first, and both
`project_invoices` rows kept pointing at it, so the owner opened milestone A's invoice and read
B's amounts. The trigger is an outbox backlog draining after a restart or a NATS outage, not an
exotic interleave.

The key is now `invoices/{projectId}/{milestoneId}-{audience}.pdf`, which is the row's own
uniqueness rule. Old rows keep their stored `pdfUrl`, so nothing needs migrating. The duplicate
number itself is untouched and is a display concern rather than a correctness one.

## Open, and needing a decision rather than a patch

### Five admin settings controls drive nothing

Verified independently, recorded in CLAUDE.md in `25e152c`.

`matching_weights`, `exploration_rate`, `auto_release_days`, `free_revision_rounds` and
`max_team_size` save to `platform_settings` and read back into the form, so the console shows
the stored value. The engines read compiled constants from `packages/shared`. Grepping
`platform_settings` across `apps/` and `packages/` returns admin-service, the admin UI, the
schema and the seed, and nothing else.

Worse than inert: `dashboard.go` writes an `admin_audit_logs` row with action `config.update`
and the new value, so the audit trail records policy changes that never took effect. The fee
bracket table is already handled correctly, shown read-only with the reason written down.

Two options, both product decisions. Make the engines read the table, which needs a cached read
path, a fallback when the row is absent, and invalidation across replicas. Or make the controls
read-only like the fee brackets and tell operators these five are code-level.

### Move the settlement authority to the transaction type

`payment.settled` already carries the authoritative `txn.Type` from the transaction row.
`settlement-consumer.ts` types the payload without it and drops it, and the HTTP callback path
does not carry it at all. Switching on it there and keeping the prefix only to recover the
milestone uuid for `REV-` orders is the real fix behind the checkout guard above. It is a
contract change across Go and TypeScript at a boundary with no contract test, which is why it is
not bundled into the fix that landed.

## Confirmed but not acted on

These carry the agents' adversarial verification. I have not re-derived them from source, and
anyone acting on one should read the code first.

Ordered by what I would look at first.

1. **Finance CSV export writes only the 50 newest rows** (`finance.tsx:136` — `const [page] =
   useState(1)`, no setter, no pagination control, `total` fetched and never read). It cannot
   produce a closed accounting period past roughly seven completed projects.
2. **One shared `resolutionNote` across every dispute card, never cleared on collapse**
   (`disputes.tsx:118`). A leftover draft pre-fills another dispute's binding decision and
   pre-enables Release, Refund and Split.
3. **Two milestone races**: `incrementRevisionCount` writes status with no compare-and-set
   (`milestone.repository.ts:227-235`) and can reopen an approved, paid, invoiced milestone;
   accepting an application has no status guard (`applications.ts:313`) and a duplicate accept
   creates a second live assignment on the next free work package.
4. **The staffing page refetches every recommended talent one at a time and silently drops any
   whose fetch fails** (`matching.tsx:85-88`, `:97`, `:127`). A 429 from the 100-per-minute
   limiter reads as "no profile" and shortens the shortlist the owner is staffing from, with
   nothing shown. Roughly 31 requests and 45 queries per page open on a three-talent team, and
   `staleTime` is 30 seconds so it repeats.
5. **Admin lists render page one only, and `DataTable` sorts that page while emitting
   `aria-sort`** (`data-table.tsx:51`). Sharpest on the DLQ viewer during an incident, where
   entries past the first hundred are unreachable.
6. **The talent dashboard fetches every `time_log` row the talent ever wrote to render one
   integer** (`use-talent.ts:221-233`). Monotonic with tenure, and no retention job exists.
7. **Missing or mismatched indexes**: `tasks` has none beyond its primary key;
   `project_applications` has only a partial index on a predicate the talent-dashboard read
   cannot imply, so both the page slice and its unbounded `COUNT(*)` sequential-scan.
8. **Unbounded reads**: `GET /time-logs/project/:id` has no pagination and refetches on every
   timer start and stop; BRD generation and revision load the entire scoping thread while the
   two chat routes in the same file cap it at 40.
9. **`extract_text` leaks a temp file on every parse failure** (`cv_parser.py:360,377` — the
    unlink is the last statement of the `try` rather than a `finally`; the correct pattern
    already exists at `routes/ai.py:1588-1601`).
10. **A fresh `httpx.AsyncClient` per embedding call** (`embedding.py:52`), roughly 23.5ms of
    SSL context construction blocking a single-worker event loop on every scoping message.
11. **notification-service dispatches one JetStream message at a time per stream**, and
    `handleTeamForming` makes two sequential HTTP calls per talent inside one. Head-of-line
    blocking of all `PROJECT_EVENTS` when Resend or Centrifugo is degraded.
12. **The admin dashboard cache never evicts and its key space is caller-controlled**
    (`dashboard.go:66`), and `GetDailyRevenue` runs a correlated LATERAL over `projects` once
    per day in the range with no index that can serve it.
13. **DLQ search fires per keystroke against an exact-match filter** labelled "Filter by event
    type", so every intermediate keystroke is guaranteed empty.
14. **Two duplicated rules**: the 10 percent revision fee is a bare literal in both React and Go
    with no gate between them, latent because the formulas agree today; and `transaction_type`
    is restated in six places, three of which disagree, so an owner's `partial_refund` renders
    with a minus sign.

## What this pass did not cover

No measurement of any kind: no profiling, no `EXPLAIN`, no load. The `gateway/` config.
Migrations except where an index or constraint was load-bearing for a finding. Auth, session
handling, CSRF, CSP and file-upload validation, which appear here only where they fell out of a
coupling finding. Temporal workflow behaviour beyond what CI already gates.

One thing worth its own look later: roughly 90 assertions across 15 web and admin test files
read the implementation with `readFileSync` and assert on its text. Some of that is deliberate
and paired with a behavioural test, as `modal-focus.test.ts` says outright. It still means a
behaviour-preserving refactor can break those tests while a behaviour-breaking edit that keeps
the text shape passes them.
